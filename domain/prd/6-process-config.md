# PRD-006：製程配置管理

> 版本：v0.1
> 日期：2026-08-14
> 狀態：草稿

---

## 1. 背景與目標

willThx 採 SaaS 自助入駐模型：工廠購買服務後，由 Admin / Maintainer 自行將產線靜態設定建入系統，包含製程站點、機台、IoT 元件。這份設定是整個平台的資料基礎——iot-adapter 接收 MQTT 時以此驗證來源、telemetry 落地時以此對應量測語意、告警規則以此綁定監控元件。

**與硬體的關係**：IoT 裝置（ESP32 等）在出廠前已燒錄 stationId、machineId、componentCode，Admin 在 SaaS 端輸入的代碼**必須與韌體完全一致**，資料方能正確對應。建議由硬體工程師提供配置清單，Admin 照表輸入。

---

## 2. 使用者與角色

| 角色 | 可執行操作 |
|------|---------|
| **Admin** | 站點 / 機台 / IoT 元件的完整 CRUD、停用、排序、複製 |
| **Maintainer** | 同 Admin（不含使用者管理，與 PRD-005 一致） |
| **Viewer** | 唯讀，可瀏覽所有設定但不可修改 |

## 3. 操作流程

### 3.1 建立站點

1. Admin 進入「製程配置 → 站點管理」
2. 點擊「＋ 新增站點」，填入：
   - 站點代碼（如 `S01`，租戶內唯一）
   - 站點名稱（如「錫膏印刷」）
   - 說明（選填）
3. 儲存後站點出現在列表末尾，sortOrder 自動排最後
4. 可透過拖拉調整站點順序（決定製程流向，影響板件追溯的時間軸排列）

### 3.2 新增機台

1. 點擊站點進入站點詳細頁
2. 在「機台列表」區塊點擊「＋ 新增機台」，填入：
   - 機台代碼（如 `S01-M01`，租戶內唯一）
   - 機台名稱（如「印刷機-01」）
   - 型號備註（選填，如「DEK Horizon 03i」）
3. 儲存後顯示於機台列表

### 3.3 複製機台

1. 機台列表中點擊某台的「複製」
2. 彈出 Dialog，預填：
   - 新機台代碼（空白，需手動輸入）
   - 新機台名稱（空白，需手動輸入）
   - 確認複製的元件清單（顯示元件數量）
3. 確認後建立新機台，同時複製所有**啟用中**的元件設定（componentCode、名稱、資料類型、單位、上報頻率、數值範圍）

### 3.4 新增 IoT 元件

元件有兩個入口，對應不同層級：

**機台層級（一般情況）：**
1. 進入站點詳細頁 → 展開機台 → 點擊「＋ 新增元件」

**站點層級（如廠務環境感測器）：**
1. 進入站點詳細頁 → 站點層級元件區塊 → 點擊「＋ 新增元件」

兩個入口填寫相同的欄位：
- 元件代碼（如 `SP-PRESSURE`，同機台/同站點層級下唯一）
- 元件名稱（如「刮刀壓力」）
- 資料類型：`TELEMETRY`（連續數值）/ `EVENT`（離散事件）
- 單位（如 `kgf`、`°C`，TELEMETRY 必填）
- 上報頻率（秒，TELEMETRY 填固定週期；EVENT 填 `0` 表示事件驅動）
- 數值正常上限（選填，供後續告警規則使用）
- 數值正常下限（選填，供後續告警規則使用）

### 3.5 停用

**停用元件：**
- 點擊元件的「停用」，元件標記為停用，不再接收該元件的 MQTT 資料
- 歷史資料保留，仍可在資料查詢中查到

**停用機台：**
- 點擊機台的「停用」，**連帶停用**該機台下所有啟用中的元件
- 確認 Dialog 列出將被連帶停用的元件數量：「此操作將同時停用 3 個 IoT 元件，確認停用？」

**停用站點：**
- 點擊站點的「停用」，**連帶停用**該站點下所有啟用中的機台與元件
- 確認 Dialog 列出影響範圍：「此操作將同時停用 10 台機台及 30 個 IoT 元件，確認停用？」
- 站點層級的元件一併停用

### 3.6 重新啟用

停用的站點 / 機台 / 元件可單獨重新啟用，**不自動連帶恢復**。
- 重新啟用站點：站點恢復啟用，但底下機台與元件仍維持停用狀態，需逐一手動啟用
- 理由：停用時各機台可能有不同原因，不應假設全部要一起恢復

## 4. 業務規則

| 規則 | 說明 |
|------|------|
| 代碼唯一性 | stationCode、machineId 在同一租戶內唯一；componentCode 在同一機台（或同一站點層級）內唯一 |
| 代碼不可修改 | 建立後 stationCode / machineId / componentCode 不可編輯（與韌體綁定，改了資料就斷） |
| 軟刪除 | 無硬刪除功能；「停用」是唯一的下線方式，歷史資料永遠保留 |
| 停用連帶 | 站點停用 → 連帶停用其下所有機台與元件；機台停用 → 連帶停用其下所有元件 |
| 重新啟用不連帶 | 恢復啟用不自動恢復底層，需逐一操作 |
| 排序 | 站點可拖拉排序，排序影響板件追溯時間軸與 Dashboard 站點順序 |
| 複製機台 | 只複製啟用中的元件；停用中的元件不複製 |
| 站點層級元件 | machineId 為 NULL，componentCode 在同站點內唯一 |
| 數值範圍 | 上下限為選填，僅供告警規則模組使用，此處只儲存，不做即時告警 |

## 5. 例外處理

| 情境 | 系統行為 |
|------|---------|
| 輸入的 stationCode 已存在 | 即時提示「站點代碼已存在」，無法儲存 |
| 輸入的 machineId 已存在 | 即時提示「機台代碼已存在」，無法儲存 |
| 輸入的 componentCode 在同層級已存在 | 即時提示「元件代碼已存在」，無法儲存 |
| 複製機台時新 machineId 已存在 | 即時提示錯誤，無法確認複製 |
| 停用有大量底層資源的站點 | 確認 Dialog 明確列出影響數量，防止誤操作 |
| Viewer 嘗試執行寫入操作 | 按鈕不顯示（前端隱藏）；後端 API 回傳 403 |

## 6. 資料說明

### 6.1 關鍵欄位

**stations**

| 欄位 | 說明 |
|------|------|
| `station_code` | 使用者定義，租戶內唯一（如 `S01`），建立後不可修改 |
| `name` | 顯示名稱（如「錫膏印刷」），可修改 |
| `sort_order` | 製程順序，拖拉排序時更新 |
| `is_active` | 軟刪除旗標 |

**machines**

| 欄位 | 說明 |
|------|------|
| `machine_code` | 使用者定義，租戶內唯一（如 `S01-M01`），建立後不可修改 |
| `name` | 顯示名稱，可修改 |
| `model` | 型號備註，選填，可修改 |
| `is_active` | 軟刪除旗標 |

**iot_components**

| 欄位 | 說明 |
|------|------|
| `machine_id` | FK machines；NULL 表示站點層級元件 |
| `component_code` | 使用者定義，同機台/同站點層級下唯一，建立後不可修改 |
| `data_type` | `TELEMETRY` / `EVENT` |
| `unit` | 數值單位，TELEMETRY 必填 |
| `report_interval_sec` | 上報頻率秒數；0 = 事件驅動 |
| `normal_upper` | 正常上限，選填，供告警模組使用 |
| `normal_lower` | 正常下限，選填，供告警模組使用 |
| `is_active` | 軟刪除旗標 |

### 6.2 多租戶隔離

所有資料表均含 `tenant_id`，所有 API 自動注入當前使用者的 `tenantId`，不可跨租戶存取。

### 6.3 生命週期

```
建立（is_active=true）
  → 編輯（代碼不可改，其他欄位可改）
  → 停用（is_active=false，資料保留）
  → 重新啟用（is_active=true）
```

## 7. 整合點

| 服務 | 關係 |
|------|------|
| **iot-adapter** | 收到 MQTT 時查詢 `iot_components`，確認 stationCode + machineId + componentCode 存在且 `is_active=true`，否則丟棄訊息 |
| **telemetry-service** | 落地 TimescaleDB 時帶入 componentCode，語意對應依此設定 |
| **Mock Simulator** | 依 `config.yaml`（與此設定對齊）產生 MQTT 訊息，stationId / machineId / componentCode 需一致 |
| **告警規則模組**（未來）| 建立告警規則時從 iot_components 選取元件，`normal_upper` / `normal_lower` 作為預設閾值建議 |
| **板件追溯**（未來）| 時間軸排列依 `stations.sort_order` 決定站點順序 |
